# Discord個人用メモBot：基本設計メモ

最終整理日：2026-11-24  
状態：段階的に実装・検証中

## 1\. 目的と基本方針

* Discord Botを自分専用の外部メモ帳として使う。
* BotとのDMに送った通常メッセージは、コマンドなしで自動保存する。
* サーバー内ではBotのメモ機能を完全に無効化し、メッセージを処理しない。
* `/ask` は必須機能。保存済みメモを参照して質問に回答する。
* AIモデルは固定せず、交換可能な構成にする。
* 可能な限り無料枠で運用する。ただし無料枠の上限・継続性は導入時に確認する。
* 個人情報に近い内容を保存する可能性があるため、利便性よりも情報保護を優先する。

## 2\. 想定アーキテクチャ

``` text
Discord DM
   ↓ Discord Gateway
Cloudflare Workers / Durable Objects 等
   ↓ HTTPS
Google Apps Script（メイン処理）
   ├─ Google Spreadsheet（メモDB）
   └─ AI API（必要な場合のみ）
```

### 構成上の注意

* GAS単独でDiscord Gatewayの常時WebSocket接続を維持する構成は避ける。
* Workers / Durable
ObjectsでGateway接続を維持する案を検討する。ただしHeartbeat、再接続処理、無料枠の制限を実装前に確認する。
* 受信イベントでは、DMかつ所有者Discord ID一致の場合だけ処理する。
* Discordのメッセージに `guild\_id`
があればサーバー由来として即時returnする。DM以外は一切処理しない。
* Bot自身のメッセージや対象外イベントも無視する。
* Discord
Gatewayの仕様・Intent・無料枠は実装時に公式情報で再確認する。

## 3\. メモDB案：Google Spreadsheet 8シート

\---

シート名                            役割

\---

`Memos`                             メモ原文、ID、分類、登録・更新日時、Discord message
ID、重要度、状態

`MemoDates`                         原文中の日付表現、基準日時、対象期間、精度、確信度、解釈状態

`MemoTags`                          メモIDとタグの対応

`TagMaster`                         タグの正式名称、別名、表記揺れ

`Relations`                         メモ同士の関係

`Projects`                          継続プロジェクトの情報

`Settings`                          ユーザー設定、重要な制約

## `Logs`                              処理履歴。本文や個人情報は記録しない方針

個人専用なので `Users` シートは不要。所有者Discord
ID等は設定として管理する。

### Memosの主な項目案

* `memo\_id`：恒久的な識別子
* `content`：原文（必ず保持）
* `category`：NORMAL / KNOWLEDGE / PROJECT
* `created\_at`：登録日時
* `updated\_at`：更新日時
* `discord\_message\_id`：二重保存防止にも利用
* `importance`
* `status`

`memo\_id`を正式な識別子とする。Spreadsheetのセル番地は行の並べ替え等で変わり得るため補助情報にとどめる。

## 4\. メモの整理ルール

### 原文とAI整理結果

* 原文は必ずそのまま保存する。
* AIによる分類、要約、タグ、関連付けは原文とは別の追加情報として保存する。
* AI処理に失敗しても、先に保存した原文は残す。
* 自動統合・自動削除は行わず、重複候補や関連性を関係情報として残す。

### 分類

* `NORMAL`：通常メモ
* `KNOWLEDGE`：知識メモ
* `PROJECT`：継続的な作業・計画

主分類は1つ。タグや関連分類は複数可。分類は後から変更可能にする。

### 日付

日付情報は次の3種類を混同しない。

1. 登録日時：Botが受信した日時
2. 対象日時：メモ本文で言及された日時・期間
3. 更新日時：メモ情報を更新した日時
* 相対日付（明日、来週など）はDiscordの送信日時を基準にJSTで解釈する。
* GASの処理時刻を基準にしない。
* 原文中の表現は変更せず、解釈結果を別途保存する。
* 「来週」「月末」など曖昧な表現は、推定・期間として保存し、確定日と区別する。
* 解釈できない場合も原文は保存する。

### タグ・関連・プロジェクト

* タグの別名や表記揺れを統一する（例：VRChat / VRC / ブイチャ）。
* 関係種別の候補：

  * `SAME\_PROJECT`
  * `SAME\_TOPIC`
  * `SUPPORTS`
  * `CONTRADICTS`
  * `UPDATES`
  * `DEPENDS\_ON`
* 古いメモを消さず、新しい情報との更新・矛盾関係を残す。
* Projectは複数メモにまたがる継続情報を束ねる。

## 5\. 保存処理フロー案

1. Discord DMを受信
2. DM・所有者チェック
3. 二重受信チェック
4. 原文を`Memos`へ先に保存
5. 日付表現を抽出・解釈
6. 分類
7. タグ生成・既存タグ照合
8. 関連メモ検索
9. 重複候補・関連性の評価
10. `Relations`更新
11. `Projects`照合
12. 必要な`Settings`確認
13. 保存完了通知

通常DMは自動保存する。スラッシュコマンドは通常メモとして保存しない。以前の`/memo`でON/OFFする方式は採用せず、DMでは常時自動保存する方向。

## 6\. コマンド案

* `/ask`：過去メモを参照してAIが回答
* `/search`：メモを直接検索
* `/edit`：メモ編集
* `/delete`：メモ削除
* `/date`：日付情報の確認・修正
* `/related`：関連メモ表示
* `/project`：プロジェクト確認
* `/settings`：設定確認・変更

初期実装では必須の`/ask`と自動保存を優先し、管理コマンドは後から追加してよい。

## 7. 検索・AI回答案

- 初期検索はキーワード・タグ検索と関連度スコアリングを中心にする。
- Embedding検索は必要になってから検討する。
- `/ask`では全メモをAIへ送らず、質問に関連する上位数件（目安5〜10件）だけを渡す。
- メモ由来の情報にはmemo_idを添える。
- 矛盾するメモや古い情報があれば、そのことを明示する。
- `/search`は保存内容を直接探し、`/ask`はメモを踏まえてAIが回答する。

### 7.1 `/ask`の回答方針（確定）

**メモを優先し、不足部分だけ一般知識で補足する。**

1. 保存済みメモを最優先して回答する。
2. メモだけでは説明が不足する場合、AIが持つ一般知識で不足部分を補足する。
3. メモ由来の情報と一般知識による補足を明確に区別する。
4. 回答の根拠となったメモIDを表示する。
5. メモにも一般知識にも十分な情報がない場合は、無理に推測せず不明と伝える。
6. 補足が不要な場合は、補足欄を省略する。

回答例：

```text
回答：
以前、PythonとFlaskを使って通知システムを作成しています。

補足：
FlaskはPython向けのWebフレームワークです。

参照メモ：
M00125、M00131

情報源：
メモ + 一般知識
```

### 7.2 一般知識の取得方法（初期方針）

- 初期実装ではAIモデルが元々持っている知識のみを使用する。
- Web検索機能は初期実装には含めない。
- 最新情報が必要な質問では、最新情報を確認できていないことを明示する。
- Web検索は将来的な拡張候補とする。

### 7.3 過去の設定・方針の適用（確定）

- ユーザーが明示的に保存した設定・方針は、関連する質問に自動適用する。
- 過去の行動や発言から推測した好みは、確定した設定として扱わない。
- 設定同士が矛盾する場合は、新しい情報を優先する。
- 重要な矛盾がある場合は、回答時にユーザーへ知らせる。
- 過去のプロジェクトの制約や決定事項も、関連する質問で参照する。

## 8\. プライバシー・セキュリティ方針

* 「AI学習に使われないこと」と「データが流出しないこと」は別問題として確認する。
* AIサービスの学習利用、データ保持期間、ログ、第三者提供、削除条件を確認する。
* 条件が確認できない場合は、メモ本文をAIへ送らない選択肢を用意する。
* AIには質問に関連する必要最小限のメモだけを送る。
* Spreadsheetはユーザー自身のGoogleアカウントで管理し、共有しない。
* APIキーはGAS Script Properties等のサーバー側に保管する。
* ログにメモ本文や個人情報を残さない。
* メモ単位で削除できるようにする。
* 無料枠でプライバシー要件を満たすAI
APIがあるかは未確定。導入時に公式条件を再確認する。
* 「絶対に流出しない」とは保証しない。

## 9\. 保存完了通知案

値がある項目だけ簡潔に表示する。通知文はAIに生成させず、GAS側で組み立てる。


セル位置は補助情報であり、恒久的な参照にはmemo\_idを使う。

## 11. AIサービスの選定・日付情報の抽出方針

### 11.1 AIサービスの選定基準

AIサービスは次の優先順位で選定する。

1. **情報の秘匿性**：入力データの学習利用、保持期間、ログ、削除条件を重視する。
2. **無料枠**：継続的に利用できる無料枠があることを優先する。
3. **処理精度**：日本語の自然文から日付・分類・タグなどを正しく抽出できること。
4. **実装の容易さ**：Python・GASからAPI経由で利用できること。

無料枠の利用条件とデータ保護条件が両立しない場合は、少額の有料利用も許容する。

### 11.2 AIサービスの比較結果

比較した主な候補：

- Cloudflare Workers AI
- GroqCloud
- OpenAI API
- Anthropic Claude API
- Google Gemini API
- Mistral AI API

現時点では **Cloudflare Workers AIを第一候補** とする。

選定理由：
- 無料利用枠が用意されている。
- 推論データをモデル学習に使用しない方針が示されている。
- API経由で利用でき、JSON形式の出力に対応するモデルがある。
- 今後Cloudflare WorkersをDiscord Gatewayの受信基盤として利用する構想とも親和性がある。

ただし、Workers AIの利用とDiscord Gatewayの接続基盤は別の機能である。AI推論だけを先に利用することも可能。

**注意事項：**
- 無料枠の上限・対象モデル・料金は変更される可能性があるため、実装時に公式情報を再確認する。
- データが学習に使用されないことと、データが一切保存されないことは区別する。
- ログや不正利用監視を含む実際のデータ保持条件を確認する。
- アカウントの年齢・利用資格など、各サービスの利用規約も確認する。
- 他サービスへの移行を容易にするため、AI API部分は交換可能な構造にする。

### 11.3 日付情報の抽出方針

当初はPythonの `dateparser` を利用して日付表現を抽出する方針だったが、日本語の自然文では解析に限界があることを確認した。

テスト結果の例：
- 「明日」：正常に解析
- 「3日後」：単独では正常に解析できるが、文章中では誤解析する場合がある
- 「来週の月曜日」：解析できない場合がある
- 「12月5日に提出する」：文章全体の解析では失敗する場合がある
- 複数の日付が含まれる文章：抽出文字列が不自然になる場合がある

このため、日付情報の抽出・解釈はAIを主役とする方針に変更する。

`dateparser` は必要に応じて補助的な解析・検証に利用できるが、単独で日付抽出を完結させることは前提としない。

### 11.4 AIによる日付抽出の処理案

1. Discordメッセージの送信日時を取得する。
2. JSTに変換する。
3. 原文を `Memos` に先に保存する。
4. 原文・送信日時・タイムゾーンをAIに渡す。
5. AIからJSON形式で日付情報を受け取る。
6. 結果を検証し、`MemoDates` に保存する。

AIの処理に失敗しても、原文は必ず保存する。AI処理は後から再実行できる構造にする。

日付情報には少なくとも次の情報を持たせる。

- `original_expression`：原文中の日付表現
- `date_type`：予定・期限・過去の出来事など
- `start_date`：期間の開始日
- `end_date`：期間の終了日
- `precision`：日・月・年・期間などの精度
- `confidence`：解釈の確信度

単一の日付として確定できない表現は、無理に確定日へ変換せず、期間・曖昧表現として保存する。

### 11.5 AI利用頻度の想定

現在の想定利用頻度：
- メモ保存：1日あたり最大5〜6回程度
- 質問を含むAI利用：1日あたり10回未満程度

この利用頻度を前提に、無料枠での継続運用を優先して検討する。

## 12. ベクトル検索の導入・検証状況（2026-11-24）

### 12.1 導入の目的

従来のキーワード検索だけでは、質問文とメモ本文で使われている単語が異なる場合に、関連するメモを見つけにくい可能性がある。

そこで、文章の意味的な近さを数値化するEmbedding（ベクトル表現）を利用し、質問に関連するメモを検索する仕組みを追加する。

初期段階では外部のベクトルデータベースを導入せず、Google SpreadsheetにEmbeddingを保存し、Python側で類似度を計算する。情報の秘匿性・無料枠・構成の簡潔さを優先する。

### 12.2 現在の構成

EmbeddingモデルにはCloudflare Workers AIの次のモデルを使用する。

- モデル：`@cf/google/embeddinggemma-2`
- ベクトル次元数：768
- 文書用入力：`title: none | text: {text}`
- 検索用入力：`task: search result | query: {text}`

文書を登録するときと質問を検索するときでは、入力の用途に応じたプレフィックスを付ける。

### 12.3 データ保存先

Google Spreadsheetに `MemoVectors` シートを追加した。

| 列 | 内容 |
|---|---|
| `memo_id` | 対応するメモのID |
| `embedding` | EmbeddingのJSON配列 |
| `model_id` | 生成に使用したモデルID |
| `dimensions` | ベクトルの次元数 |
| `updated_at` | ベクトルの更新日時 |

Embeddingはメモ本文とは別に保存し、`memo_id` で `Memos` と対応付ける。同じ `memo_id` のベクトルを再保存した場合は、既存データを更新する。

### 12.4 実装済みのGAS処理

#### `save_embedding`

- メモIDとEmbeddingなどの情報を受け取り、`MemoVectors` に保存する。
- 同じメモIDが存在する場合は更新し、存在しない場合は追加する。
- 保存先シートが存在しない場合はエラーとして扱う。

#### `get_memo_vectors`

- 有効なメモに対応するベクトルだけを取得する。
- `Memos` と照合し、削除・無効状態のメモに紐づくベクトルを検索対象から除外する。
- モデルIDが `@cf/google/embeddinggemma-2` であることを確認する。
- 次元数が768であることを確認する。
- Embeddingが正しいJSON配列であり、数値が有限値であることを検証する。
- Python側へ `memo_id`、`content`、`created_at`、`embedding`、`model_id`、`dimensions` を返す。

### 12.5 Python側の実装・テスト

以下の独立したテストファイルを作成した。

- `test_save_embedding.py)：Embeddingの保存テスト
- `test_get_memo_vectors.py)：保存済みEmbeddingの取得・形式検証
- `test_cosine_similarity.py)：コサイン類似度の計算テスト
- `test_vector_search.py)：質問のベクトル化、メモ取得、類似度計算、順位付け、回答生成の一連のテスト

Embedding生成関数 `generate_embedding(text, input_type)` は `test_cloudflare_ai.py` に実装している。同期関数であり、`await` は付けずに呼び出す。

コサイン類似度は、2つのベクトルの向きの近さを計算する。値の目安は次のとおり。

- 1.0：同じ方向
- 0.0：直交する方向
- -1.0：反対方向

次元数の不一致やゼロベクトルなども検証する。

### 12.6 検証結果

#### 保存・取得

- `save_embedding` による保存に成功。
- `get_memo_vectors` による取得に成功。
- 取得したEmbeddingの次元数が768であることを確認。
- コサイン類似度の基本テスト（同じ方向・直交・反対方向）がそれぞれ1.0、0.0、-1.0となることを確認。

#### ベクトル検索

### 12.7 回答生成との接続テスト

ベクトル検索で得た上位3件のメモを、既存の `generate_memo_answer(question, memos)` に渡すテストを追加した。

回答生成AIには、次の情報を渡す。

- `memo_id`
- `content`
- `created_at`

テストでは、次の結果を確認した。

- 「テストの範囲」への質問に対し、数学のテスト範囲が微分全般であると回答した。
- プログラミング言語についての質問に対し、Pythonの代わりにJavaScriptを検討していたと回答した。
- どちらも参照したメモIDが出力された。
- 今回の2件では、メモにない一般知識の補足は出力されなかった。
